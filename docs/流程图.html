02一次任务的完整时序server.py + loop.py

这张最关键——它说明了确认闸到底是什么：agent 线程真的阻塞在 threading.Event.wait() 上，页面轮询看到 pending 才画出闸口，用户点确认才把线程放行。

sequenceDiagram
  autonumber
  participant B as 浏览器
  participant F as FastAPI 主线程
  participant S as Session
  participant A as Agent 后台线程
  participant M as 千问
  participant T as 工具层

  B->>F: POST /send goal
  F->>S: start 抢运行权
  Note over S: 已在跑则返回 409
  F->>A: 起后台线程
  F-->>B: 200 ok

  loop 每 1 秒
    B->>F: GET /poll
    F-->>B: events pending plan running
  end

  A->>M: chat messages 加 schemas
  M-->>A: tool_calls 为 write_file
  A->>S: confirm 带 diff 预览
  Note over A: 阻塞在 Event.wait

  B->>F: GET /poll
  F-->>B: pending 非空
  Note over B: 流里画出橙色闸口
  B->>F: POST /approve ok=true
  F->>S: resolve 触发 Event.set
  S-->>A: 返回 True

  A->>T: execute write_file
  T-->>A: 已写入 并逐代备份
  A->>A: 熔断计数 加 压缩 arguments
  A->>M: chat 带上工具结果
  M-->>A: content 且无 tool_calls
  A->>S: emit final
  A->>S: running 置 False
  B->>F: GET /poll
  F-->>B: final 事件
读法：第 12~18 步之间 agent 线程是停住的，FastAPI 主线程照常响应轮询。这就是把确认画成"流里的闸"而不是浮层弹窗的原因。

03run_agent 单步控制流agent/loop.py:54-100

循环体上限 20 次。三处护栏的位置：裁剪在请求前，熔断在工具执行后，参数压缩在整批工具跑完后。

flowchart TD
  START([收到目标]) --> INIT["messages 等于 system_prompt 加 user goal"]
  INIT --> LOOP{"step 未超 max_steps"}
  LOOP -->|否| MAXOUT["emit final 已达最大步数"]
  LOOP -->|是| TRIM["trim_history
按 assistant 加其 tool 响应 整组裁剪"]
  TRIM --> STEP["emit step
n / max / chars"]
  STEP --> CHAT["llm.chat"]
  CHAT --> HASCALL{"有 tool_calls"}
  HASCALL -->|没有| FINAL["emit final 返回回答"]
  HASCALL -->|有| APPEND["把 assistant.tool_calls 写进历史
OpenAI 协议要求"]
  APPEND --> EACH["逐个处理 tool_call"]
  EACH --> NEEDC{"需要确认"}
  NEEDC -->|是| WAIT["confirm 阻塞等前端"]
  WAIT --> OKQ{"用户放行"}
  OKQ -->|否| SKIP["result 为 用户拒绝了该操作"]
  OKQ -->|是| EXEC
  NEEDC -->|否| EXEC["tools.execute
异常转成错误字符串"]
  EXEC --> COUNT["按 工具加参数加结果 计数"]
  COUNT --> ABORT{"次数达到 3"}
  ABORT -->|是| DEAD["emit final 判定死循环 终止"]
  ABORT -->|否| NUDGE{"次数等于 2"}
  NUDGE -->|是| HINT["结果后追加系统提示
别重复 换方法"]
  NUDGE -->|否| EMIT
  HINT --> EMIT["emit plan 或 tool"]
  SKIP --> EMIT
  EMIT --> MORE{"还有 tool_call"}
  MORE -->|有| EACH
  MORE -->|没有| SHRINK["_shrink_tool_args
压掉已执行完的超长参数"]
  SHRINK --> LOOP

读法：橙色是三处护栏。熔断按「工具 + 参数 + 结果」计数而不是按异常——工具失败时大多返回错误字符串，只数异常几乎永远不触发。

04安全阀判定safety/commands.py + sandbox.py

命令用只读白名单而不是危险名单——危险名单拦不住 dir && del /f /s /q * 这类组合，两天做不出可靠的命令解析器，所以反着做。

flowchart TD
  IN([工具调用]) --> W{"是 write_file"}
  W -->|是| CONF["需要确认
先给 diff 预览"]
  W -->|否| R{"是 run_command"}
  R -->|否| PASS["自动放行
list_dir · read_file · search_in_files
web_search · update_plan · save_memory"]
  R -->|是| META{"含 shell 元字符或换行"}
  META -->|含| CONF
  META -->|不含| ARG{"参数越界
上跳 或 盘符 或 绝对路径"}
  ARG -->|越界| CONF
  ARG -->|没有| HEAD{"首个 token 在白名单"}
  HEAD -->|"dir ls type cat pwd echo whoami"| PASS2["自动放行"]
  HEAD -->|"git status / diff / log"| PASS2
  HEAD -->|"python 或 pip 的版本与 list"| PASS2
  HEAD -->|其它| CONF

  PASS --> SB
  PASS2 --> SB["路径类工具再过一道沙箱
resolve 加 commonpath
越界抛 SandboxError"]
  CONF --> GATE(["页面弹确认闸
确认 / 拒绝"])

  classDef gate fill:#fdf1e0,stroke:#c79245,color:#3a2a12
  classDef ok fill:#e9f4ed,stroke:#4d9a6c,color:#173423
  class CONF,GATE gate
  class PASS,PASS2 ok
读法：元字符表是 &&、||、|、;、>、<、&、反引号、$(， 以及换行与回车——少了后两个，dir\ndel x 会被判为只读直接放行。参数里的 .. 也要拦： run_command 不经过沙箱，白名单里的 type/cat 否则能读到工作目录之外。

05事件类型对照loop.py emit → /poll → index.html

后端只往队列里塞这五种事件，页面按类型渲染。加一种新事件只需改这三处。

type字段页面表现
stepn · max · chars顶部步数、右栏上下文占用条
assistantcontent🤖 思考文本
plansteps[]右栏计划面板 + 一张 update_plan 卡片
toolname · result⚙ 工具卡片，拒绝时标红
finalcontent✅ 绿框收尾（出错时为红框）
注意：pending 不走事件队列——它是 /poll 的独立字段，因为确认是状态不是事件：页面刷新后闸口必须还在。

这几张图和设计文档差在哪

  • 文档 §3 的"完整循环"只有规划 → 执行 → 反思三步，没有熔断、上下文裁剪、参数压缩——这些都是后来补进 §13 健壮性护栏的，但从没画进流程。
  • 确认闸的阻塞语义在文档里完全看不出来。§9 只说"后端进入待确认状态"，没说清是哪个线程停住、谁在等谁。这是图 02 存在的理由。
  • 反思在图里是隐形的。文档把"出错→反思→重试"画成一个环，但代码里没有对应分支——它靠的是把错误字符串喂回历史 + system prompt 第 3 条，模型自己决定要不要换方法。图 03 里那个"追加系统提示"是唯一一处代码层面的强制反思。
