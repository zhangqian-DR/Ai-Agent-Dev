02一次任务的完整时序server.py + loop.py

这张最关键——它说明了确认闸到底是什么：图跑到闸前存 checkpoint 然后返回，后台线程就此结束。等待确认期间没有任何线程挂着；用户点确认后，另起一个线程用 Command(resume=…) 从 checkpoint 接着跑。

读法：两条驱动线程互不重叠——第一条在闸前就退出了。这正是换成 interrupt 换回来的东西：关掉页面不会挂住任何东西，隔多久回来那道闸都还在。
恢复那一步（Command resume 之后）：tools 节点整个从头重跑，所以闸必须在任何副作用之前、且一轮只有一个——这就是"一轮里的危险操作合成一张卡"的由来。这条是写代码前用一个最小图实测确认的，不是照文档推的。
最后的 verify 节点只在配了 verify_cmd 且这一轮真动过东西时才出现。

03图的三个节点（fast 路）agent/loop.py build_graph

这张画的是 fast 那条路。slow 在它两头各加了 planner 与 synth、再接一道 critic，中间这段执行是同一段代码——见图 06。
recursion_limit 等于 max_steps × 2——它数的是节点执行次数，一个 ReAct 回合是 agent 加 tools 两个节点。三处护栏的位置：裁剪在请求前，熔断在工具执行后，参数压缩在整批工具跑完后。

读法：橙色是护栏。熔断用两把尺子：同参同果累计抓交替死循环，同参连续抓 run_command 那种输出带时间戳、逐字比对永远不相等的情况。
interrupt 那一格是虚线回边：第一次抛出让图返回，恢复时整个节点重跑而这一行直接返回放行结果——所以它上面只能算预览，动手必须在它下面。

04安全阀判定safety/commands.py + sandbox.py

命令用只读白名单而不是危险名单——危险名单拦不住 dir && del /f /s /q * 这类组合，两天做不出可靠的命令解析器，所以反着做。

读法：判定是 fail-closed 的——自动放行是一份显式白名单，没列进去的一律要确认， 包括不认识的工具名。反过来写（"认识的危险工具才拦"）的话，以后加一个会写盘的工具、忘了同步改白名单， 它就静默地自动放行。
元字符表是 &&、||、|、;、>、<、&、反引号、$(、%， 以及换行与回车。少了换行，dir\ndel x 会被判为只读直接放行；少了 %， type %USERPROFILE%\.ssh\id_rsa 会被放行——cmd 展开变量发生在参数检查之后。 python -c "任意代码" --version 也曾被放行过：那时开关只要出现在任意位置就算数， 现在必须是「解释器 + 唯一的查看开关」两个 token。

05事件类型对照loop.py emit → /poll → index.html

后端只往队列里塞这五种事件，页面按类型渲染。加一种新事件只需改这三处。

type字段页面表现
stepn · max · chars顶部步数、右栏上下文占用条
assistantcontent🤖 思考文本
plansteps[]右栏计划面板 + 一张 update_plan 卡片
toolname · result · ok · badge?⚙ 工具卡片，ok=false 时标红；badge 可覆盖角标措辞
finalcontent · ok✅ 绿框收尾，ok=false 时红框
注意：pending 不走事件队列——它是 /poll 的独立字段，因为确认是状态不是事件：页面刷新后闸口必须还在。载荷是 {id, actions: [{name, preview}…]}，一轮里的危险操作合成一张卡；id 递增，页面靠它判断"这张卡我画过没有"。
ok 是结构化标志，不是从文案开头猜的——不然模型正常回答只要以"出错："开头就会被渲染成错误。落库时对应 messages.status（error / rejected），回放才还原得出来。
badge 是可选的：验收闸失败该说"未通过"而不是复用"已拒绝"。颜色仍按 ok 走，只有措辞由发事件的一方决定。

06三路分诊agent/router.py + loop.py build_graph

读法：判错的代价不对称，所以规则往上偏——把闲聊判成 fast 只是多花点 token，把真任务判成 direct 则是让模型没有工具、只能凭空编。因此 direct 收得很窄，认不出来的一律走 fast。
绿色那条是最省的：tools 传空列表不只是省 token（实测一次「你能做什么」input_tokens 从 1131 降到 142），更是把「回答问题」和「能动手」物理隔开——绑不上工具，模型就算想写文件也写不出来。
critic 只在没有机器判据时才起：配了 verify_cmd 的项目，测试绿不绿是客观的，比让模型评自己可靠，那条路由 verify 管着；两个判官并存只会互相打架。
执行没有并行，而且大概率会一直串行。实测一轮 slow 任务里模型调用占 95.9%、工具执行占 0.1%，把工具改成理想并行最多省总时长的 0.1%。

这几张图和设计文档差在哪

  • 文档 §3 的"完整循环"只有规划 → 执行 → 反思三步，没有熔断、上下文裁剪、参数压缩——这些都是后来补进 §13 健壮性护栏的，但从没画进流程。
  • 确认闸的语义在文档里完全看不出来。§9 只说"后端进入待确认状态"，没说清停在哪、谁在等谁。这是图 02 存在的理由——而它的答案已经变了一次：早期是 agent 线程阻塞在 threading.Event.wait() 上，现在是图存 checkpoint 后返回、根本没有线程在等。
  • 反思现在有两处是硬的了。文档把"出错→反思→重试"画成一个环，但早期代码里没有对应分支——它靠的是把错误字符串喂回历史 + system prompt 第 3 条，模型自己决定要不要换方法。现在图 03 里有两处是流程强制的：熔断的"追加系统提示"，以及 verify 节点把验收失败喂回去。后者更接近文档想画的那个环，只是判据是机器给的（测试绿不绿），不是模型自评。
  • 文档完全没有 LangGraph。它写的是手写 for 循环。现在循环由 StateGraph 驱动、确认闸由 interrupt 加 SqliteSaver 实现，这几张图是以代码为准重画的。
  • 文档里只有一条执行路径。现在是三条（图 06）：direct 直答不绑工具、fast 是原有的 ReAct、slow 走规划-汇总-反思。文档 §3 那个"规划 → 执行 → 反思"的环，现在只在 slow 这一条上成立，而且判据优先用机器的（测试绿不绿）而不是模型自评。
